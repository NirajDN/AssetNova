## 1. 🌟 Section 1: Project Mission & The Digital Foreman

### 1.1 What is AssetNova?
AssetNova is a **Software as a Service (SaaS)** platform for inventory management. In the industrial world, machine spares, tools, and components are often managed with paper logs or disconnected spreadsheets. This leads to "Inventory Drift"—where the digital record doesn't match the physical shelf.

AssetNova solves this by providing a professional-grade, multi-tenant system. Instead of one app for one factory, we built a "Digital Landlord" system. Multiple companies (Tenants) can sign up, and each gets its own private, isolated workspace.

### 1.2 The "Digital Foreman" Philosophy
A **Foreman** is a worker who oversees a workshop with both technical knowledge and authority. Our software acts as this Foreman electronically:
- **Authority**: It enforces strict validation (no negative stock, no unauthorized edits).
- **Visibility**: It provides real-time "Stock Trajectory" analytics.
- **Organization**: It forces clear mapping between Parts, Categories, and Suppliers.

## 2. ⚙️ Section 2: Modern Stack Architecture (The Engine Room)

We chose a "Modern Monolith" stack based on **PHP 8.2** and **Laravel 12 (Stable)**. 

### 2.1 The Backend: Laravel 12 (Stable)
Laravel was selected for its robustness and security features:
- **Routing Engine**: Maps URLs to code logic with millisecond latency.
- **Eloquent ORM**: An Elegant Object-Relational Mapper that turns database rows into "Smart Objects".
- **Blade Templates**: The engine that compiles HTML on the server, ensuring private data never leaks to the client in raw form.
- **Middleware Layer**: The "Bouncer" that handles security checks before the code even runs.

### 2.2 The Language: PHP 8.2+
Modern PHP is highly optimized. We use version 8.2 to take advantage of:
- **Readonly Properties**: Ensuring internal configuration cannot be tampered with.
- **Constructor Property Promotion**: Making the code cleaner and easier to maintain.
- **Strong Typing**: Specifying that a `PartID` must be an integer, preventing entire classes of bugs.

### 2.3 The Database: MySQL 8.0
MySQL acts as the "Truth Center". 
- **ACID Compliance**: Ensures that if a stock movement happens, it's either 100% saved or 100% rolled back.
- **Relational Integrity**: If you try to delete a category that still has parts in it, the database will block the action to prevent data corruption.
- **Search Optimization**: We use B-Tree indexing on `company_id` and `sku` columns for rapid lookups.

### 2.4 The Frontend: TailwindCSS & Alpine.js
We used the **TALL Lite** approach for premium interactivity:
- **TailwindCSS**: Utility-first styling. We don't write CSS; we use utility classes like `p-4`, `bg-primary`, and `rounded-xl` that ensure the design is consistent.
- **Alpine.js**: Provides "Snappiness". When you click a menu or open a modal, Alpine handles the animation instantly without waiting for the server.

## 3. 🏢 Section 3: The Multi-Tenant Engine (Data Isolation)

The most advanced feature of AssetNova is **shared-schema multi-tenancy**. 

### 3.1 The Concept of Isolation
Companies A and B share the same hardware and the same database tables (efficient for hosting), but they can **never** see each other's data.

### 3.2 The Master Filter: `$this->cid()`
Inside every controller, we have a security helper:
```php
private function cid(): int { return Auth::user()->company_id; }
```
This is used in every query. For example, to list parts:
```php
$parts = Part::where('company_id', $this->cid())->get();
```
Even if a user is "Logged In", they can only see rows tied to their specific `company_id`.

### 3.3 Protection Against "ID Probing"
If a user tries to manually visit `/parts/500`, but part 500 belongs to a different company, the server executes:
```php
abort_if($part->company_id !== $this->cid(), 403, 'Unauthorized.');
```
This 403 "Forbidden" screen is our primary defense against data leaks and vertical privilege escalation.

## 4. 🗄️ Section 4: Database Master Blueprint

Here is exactly how the data is organized.

### 4.1 Table: `companies` (Tenants)
- `id`: BigInt Primary Key.
- `name`: Official business name.
- `slug`: URL-friendly identifier for branding.
- `industry`: Industry segment (used for future analytics benchmarking).
- `logo_url`: Path to the tenant's brand asset.

### 4.2 Table: `users` (Identity)
- `company_id`: Foreign key link.
- `role`: `super_admin` (Full access) or `company_admin` (Tenant access).
- `name`: Full name.
- `email`: Login identifier.
- `password`: Hashed using **Argon2id** (High security).

### 4.3 Table: `parts` (Inventory Assets)
- `sku`: Unique Shop Keeping Unit (Barcode).
- `name`: Description of the spare.
- `cost`: Decimal value of the item.
- `stock_quantity`: Current inventory level.
- `min_threshold`: Reorder safety point.
- `location`: Physical shelf/bin coordinates.

### 4.4 Table: `transactions` (Audit Ledger)
- `part_id`: Foreign key link.
- `type`: `in` or `out`.
- `quantity`: Positive integer.
- `notes`: Audit context (Max 500 chars).
- `created_at`: The exact millisecond of the movement.

## 5. 🎮 Section 5: Core Logic Spotlights

### 5.1 The "Masquerade" Module (Impersonation)
Built for technical support and troubleshooting.
1. **Request**: Super Admin navigates to `/control-tower/impersonate/{userId}`.
2. **Session Persistence**: The system writes `impersonator_id` to the session.
3. **Authentication Swap**: `Auth::login($targetUser)` is called.
4. **Conditional Layout**: The layout file detects the session key and enables the "Platform Master Mode" banner.
5. **Reversion**: The `stopImpersonating` method resets the session and restores the Super Admin identity.

### 5.2 The Stock Ledger Logic (IN/OUT)
When a user records a movement (e.g., Stock Out 5 units):
1. **Ownership Validation**: The controller verifies the `part_id` belongs to the current `cid`.
2. **Stock check**: `if ($part->stock_quantity < $request->quantity)`.
3. **Database Write**: `Part::decrement('stock_quantity', $quantity)`.
4. **Permanent Audit**: A row is added to `transactions`. This makes the data "Auditable"—you can never delete a piece of history.

**NEW: Automated Logging Interlocks**
- **Creation Audit**: When a new part is registered with "Opening Stock", the system automatically creates a "Stock In" transaction with the note: *"Initial stock registration on part creation."*
- **Adjustment Audit**: If an admin manually edits the "Stock Quantity" field in the Part Editor, the system calculates the difference (`new_qty - old_qty`) and automatically records an "Adjustment" transaction to ensure the history always matches the shelf count.

### 5.3 Analytics Engine (Chart.js Data Mapping)
The Dashboard uses a sophisticated data pipeline:
- **Monthly Aggregation**: It queries the `transactions` table for the last 6 months.
- **Weighting**: It sums the total quantity for `in` types vs `out` types per month.
- **Visualization**: The resulting arrays are passed as JSON to the Chart.js plugin for canvas rendering.

## 6. 🛡️ Section 6: Security: The "Iron Dome" Architecture

### 6.1 CSRF (Cross-Site Request Forgery)
Protects against malicious websites sending requests to AssetNova in your name. Every form must include a hidden secret token.

### 6.2 XSS (Cross-Site Scripting)
Blade templating engine automatically sanitizes all user input. If a user tries to inject `<script>` tags, they are converted to text and displayed harmlessly.

### 6.3 SQL Injection (PDO)
We never use "Raw SQL". Everything goes through the **Eloquent ORM**, which uses parameterized queries to ensure data and commands are separated.

## 9. 📂 Section 9: File Management & Storage Hygiene

### 9.1 Renaming Patterns
Uploaded files are renamed using a combination of timestamps and part IDs to prevent overwriting:
`part_` + `timestamp` + `extension`.

### 9.2 Automatic Cleanup
When a Part is deleted, the system doesn't leave the image behind. It uses PHP's `@unlink` to remove the physical file from the `/public/images/parts` directory.

## 10. 🔄 Section 10: Detailed Request Lifecycle Trace

### Trace A: Recording a Manual Movement
1. **Browser**: User clicks "Record Stock IN".
2. **Web Server**: Receives POST request on `/transactions`.
3. **Middleware Chain**:
   - `EncryptCookies`: Decrypts user data.
   - `StartSession`: Loads the user session.
   - `VerifyCsrfToken`: Ensures the request is legitimate.
   - `EnsureAuthenticated`: Verifies the user is logged in.
4. **Controller Action**: `TransactionController@store` validates the quantity and SKU.
5. **Model Logic**: Decrements inventory and creates the transaction audit.
6. **Redirect**: Sends a 302 status code back to the browser with a "Flash Message".

### Trace B: Automated Audit on Part Creation
1. **Browser**: User submits "Add New Part" with 150 units of "Opening Stock".
2. **Controller**: `PartController@store` logic executes.
3. **Model A**: `Part::create()` saves the basic part data and quantity.
4. **Model B (Automated)**: The controller detects `quantity > 0` and immediately calls `Transaction::create()` with a reference to the new Part ID.
5. **Result**: The Parts Directory shows 150 units, and the Transaction Log shows the "Incoming" movement from the moment of creation.

## 11. 📘 Section 11: Technical FAQ for Project Review

**Q: How do you handle password security?**
A: We use **Argon2id hashing**. We never store plain text. Even if our database was compromised, the hashes are practically impossible to crack.

**Q: Why not use individual databases for every tenant?**
A: In a multi-tenant platform with hundreds of small tenants, individual databases are too slow to update and expensive to host. Shared-schema is the industry standard for performance and scalability.

**Q: How is "Stock at Risk" calculated?**
A: It is a dynamic query that filters for all parts where `stock_quantity <= min_threshold`, then multiplies each missing item's quantity by its `cost` to show potential financial impact.
